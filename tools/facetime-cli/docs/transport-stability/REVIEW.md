# Relay repair review

The real installed CLI exited 6 at 14:32:27.019 UTC with no retained entries. A concurrent relay-host authority probe hit its 2,000 ms timeout at 14:32:27.587 UTC, and another timeout occurred a minute earlier. The old relay closes on any polling exception. This is evidence for transient authority failures as a concrete trigger, not proof of the underlying network/service latency cause.

Predicate changed: one failed, replayable authority poll no longer immediately discards an authenticated WebSocket when an authorized retry can complete within its last confirmed lease. There is exactly one retry, delayed 100 ms. Each request still has a maximum 2,000 ms budget; the retry receives less time if necessary to remain within the conservatively tracked five-second lease. No decision/connect/ack replay was introduced. No readiness or incoming decision budget changed, and the supervisor's three starts per lifetime remain unchanged.

The first regression was red against the original relay: a stalled first poll closed the socket instead of delivering after recovery. The green suite additionally verifies HTTP 401/403 closes without retry, repeated outage closes after two polls, role change after retry forwards no stale frames, malformed response never retries or leaks its body, a decision failure is sent once, a reset connection recovers without minting another generation, and slow connection acquisition cannot extend the retry past the existing lease.

Combined reviewer conclusions: authorization is rechecked by the existing backend on every retry, including generation/revocation fencing. No authority result or incoming frame is synthesized or cached during outage. Confirmed lease time starts before the request, which is conservative relative to database renewal. Failed/uncertain requests cannot extend it. Recovery credentials and scope are unchanged. Diagnostics contain fixed categories, action names and numeric status only. Frozen original artifacts and production journals must remain untouched; deploy a new relay archive and restart the application once after the replacement is healthy.

Physical media validation is outside this repair's authorization. Complete the standby observation and evidence before proposing activation.

## Freshness follow-up review

The later evidence invalidated the initial ten-minute qualification: local network failures and wall-clock suspension interrupted observation, generation changed, and at 19:24 UTC the backend lease had expired despite healthy local IPC and an established Node TCP socket. The exact socket/proxy cause remains unresolved. The original poll retry is retained, with a separate availability watchdog rather than increased retries.

Three CLI regressions were red against the deployed transport: silent socket, unrelated pings and heartbeat loss. The relay heartbeat test was red against the frozen r2 relay. Green suites on Node 22/24 report 267 CLI passes, four existing skips, no failures, and 13 relay passes. A heartbeat is emitted only after successful authority polling and role validation, at most once per second. No independent timer or failed poll emits it. The CLI starts a five-second watchdog on welcome and resets it only for the exact control-ping marker on the current socket; socket closure clears it. Timeout terminates the socket and uses existing disconnect/cleanup plus the unchanged bounded supervisor policy. The signal is transport freshness, not acceptance authority or media readiness.

The new application context differs only in cli.tgz, its lockfile integrity and inputs manifest. The new CLI archive differs only in compiled connector-wire.js. Runtime supervision, UID, dependencies, Python owner, handler path, persistent scope, journals and configuration remain unchanged. The relay must be deployed first. Standby observation must run on the remote host so a local laptop/network interruption does not invalidate timing. No activation or provider staging is authorized by this repair.
